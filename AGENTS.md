# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Werewolf is a Spigot/Bukkit Minecraft server plugin (`com.dogonfire.werewolf`), built with Maven against `paper-api` 26.3 (runtime minimum 26.1, enforced by `api-version` in `plugin.yml` and the Java 25 bytecode). It must still run on Spigot: the only Paper-only API calls live in `disguises/PaperSkinFactory`, which is only loaded after a runtime check. Source targets Java 25 (`maven.compiler.release` in `pom.xml`), which 26.x servers require anyway; CI (`.github/workflows/build.yml`) builds on JDK 25 for every push and PR; pushing a tag equal to the pom version (e.g. `0.12.0`) publishes a GitHub release with the jar.

## Commands

```bash
nix develop                # devshell with JDK 25 + Maven (flake.nix); prefix commands with `nix develop -c` otherwise
mvn clean package          # default goal; produces target/Werewolf-<version>.jar
mvn -B clean package       # what CI runs (there are no unit tests; this only checks it compiles)
```

- There is no test suite. You can only check that it compiles; to check behavior, drop the jar into a Spigot server's `plugins/` folder.
- Non-standard layout: `sourceDirectory` is `src/` (packages live directly under `src/com/...`), and resources come from `src/resources/` with Maven filtering on (`plugin.yml` gets `${project.version}`).
- All plugin dependencies (Vault, LibsDisguises, SkinsRestorer, WorldGuard, PvPManager 4.x, GriefPrevention, PlaceholderAPI, Vampire) are `provided` and resolved from the third-party repos listed in `pom.xml`. If one of those repos is unreachable, the build fails.
- Releases bump `<version>` in `pom.xml` (e.g. "Bump to v0.11.0"), then push a tag with the same version (e.g. `0.11.0`); CI attaches the jar to a GitHub release. Work goes to the `dev` branch and is merged into `master` through a PR.

## Architecture

**Central singleton.** `Werewolf.java` (the `JavaPlugin`) is the hub:
- It holds the current `config/Settings` (`getSettings()`, reached as `plugin.getSettings()` or `Werewolf.instance().getSettings()`). See **Configuration** below.
- It holds every manager in a static field, reached through static getters (`Werewolf.getWerewolfManager()`, `getClanManager()`, …). Other code calls these getters and `Werewolf.instance()` instead of receiving its dependencies.
- It holds the `storage/Storage` (`Werewolf.getStorage()`); see **Storage** below.
- `onEnable()` sets things up in an order that matters: `new Storage(...).load()` (reads every data file) → `loadSettings()` (so every constructor can read settings; also creates and registers `TrophyManager`/`SignManager` when enabled) → construct managers and listeners → detect a disguise plugin → detect optional plugins (Vault turns on `HuntManager`, bounties and signs; also Vampire, HealthBar, PlaceholderAPI) → register listeners → `clanManager.load()`/`languageManager.load()` → recipes → repeating tasks (including the storage flush). Some managers are only created when a feature is on (`huntManager` needs Vault, `werewolfScoreboardManager` needs `Scoreboards.Enabled`, `trophyManager`/`signManager` need `Trophies.Enabled`/`Signs.Enabled`), so they can be null.

**Configuration.** `src/resources/config.yml` is the single source of defaults: every key with its default and a comment (it is Maven-filtered, so never write `${` or `@` in it). `saveDefaultConfig()` writes it on first start; after that Bukkit uses the bundled file as defaults, so keys missing from the admin's file get the bundled value. The plugin never rewrites config.yml except in `config/ConfigMigrator`, which runs at every (re)load: it reads `config-version` (missing = 1), backs up the old file once to `config.v<old>.bak`, upgrades it (v1→v2: `WerewolfWolf.*`/`Infection.CurePotionChance` renames, swapped Bloodmoon/Silvermane skins, removing dead keys) and writes it atomically; it refuses to touch a file that does not parse. `config/SettingsLoader` then builds the immutable `config/Settings` record (one nested record per section: `general()` = `Settings.*` plus the one-key sections, `moon()`, `wolfForm()`, `infection()`, `items()`, `clans()`, …), clamping/logging invalid values and parsing effects, materials, UUIDs and enums. It reads keys without Java defaults (`getInt(path)`), except per-clan `Werewolf.Stats.*` which fall back to the global `Werewolf.*` values when the file does not set them. To add an option: add the key to config.yml, a record component in `Settings`, and read it in `SettingsLoader`; if a key is renamed or removed, bump `ConfigMigrator.CURRENT_VERSION` and `config-version`, and add a migration step. `/ww reload` (`reloadSettings`) re-reads the file, re-runs the migrator and loader, calls `Storage.reload()` and reloads clan skins/names and language; things set up once in `onEnable` (listeners, recipes, scoreboards, repeating tasks) are not rebuilt.

**Main game loop.** A sync repeating task calls `WerewolfManager.update()` every 100 ticks. It checks every online werewolf for transform/untransform, and gives one random player a chance at an "urge" message. That method handles night/full-moon transformations, the `/ww transform` time limit, infection progress and auto-cure. Moon phase and night timing live in `managers/MoonManager` (`getMoonPhase`, `isNight`, `isFullMoonNight`, `isTransformationNight` = the nights the moon forces outdoor werewolves to transform, `setMoonPhase`, dusk announcements); `isUnderOpenSky` and `isWerewolvesAllowedInWorld` (`AllowedWorlds`; empty = the main world) are on `Werewolf`. Clans update on a separate 72000-tick task.

**Levels.** A werewolf's level is `WerewolfManager.getNumberOfTransformations` (`Transformations` in `werewolves.yml`); `Maturity.*` config keys are the levels that unlock perks. `grantFullMoonLevel` adds one level per transformation night, guarded by `LastLevelNight` so relogging doesn't grant more. Wolf forms entered with `Reason.CONTROLLED` are tracked in memory: they are not reverted at morning but expire after the `Transformation.*` time limit (`Reason.TIME_LIMIT`); every other wolf form is reverted at morning. Cooldowns (transform/howl/growl) are in memory too.

**Alphas.** Each clan's alpha UUID is in `clans.yml` (`ClanManager.getAlpha` is a plain read). `ClanManager.checkAlphas()` runs from `WerewolfManager.update()` and fills empty or stale slots with `WerewolfManager.getAlphaCandidate` (full werewolves first, then highest level); `setWerewolfClan` and `unmakeWerewolf` (via `removeAlpha`) hand the slot on immediately. `listeners/AlphaListener` moves the alpha to a same-clan killer, or to the runner-up when a human kills the alpha (`Hunting.Enabled`), and on `NewAlphaEvent` (MONITOR) re-skins the old and new alpha a tick later through `WerewolfManager.refreshWerewolfSkin` (`Reason.REFRESH`). Admin commands `setlevel`/`addlevel`/`setalpha`/`cure` resolve names through werewolves.yml and known offline players, so they work on offline werewolves.

**Events.** `events/` holds cancellable Bukkit events fired at the choke points (plus `TrackerTargetEvent` and `WerewolfSniffEvent`, see Hunting gear): `WerewolfInfectionEvent` (`WerewolfManager.makeWerewolf`), `WerewolfCureEvent` (`unmakeWerewolf`), `WerewolfTransformEvent` (`setWerewolfSkin`/`unsetWerewolfSkin`, cancelling is ignored for `Reason.FORCED`) and `NewAlphaEvent` (`ClanManager.assignAlphaInClan`). Each of those methods takes a reason/cause and returns whether it went ahead; new code that changes werewolf state should go through them, and features that need to veto or react to a change should listen to these events instead of adding checks at every call site.

**Wolf form.** `managers/WolfFormManager` owns what wolf form does to a player: per-clan `Stats` (speed, defense = multiplier on incoming damage, fist/item damage; separate alpha values, read in `DamageListener`), per-clan potion effects (`Werewolf.Effects.<ClanType>`, `NAME:amplifier:duration`), blocked potions and the diet's food list. `DisguiseTask` calls `applyWolfForm`, `WerewolfManager.update()` calls `refreshWolfForm` for everyone in wolf form, and `UndisguiseTask`/join call `removeWolfForm`, which removes only the effects it applied. The config lists are parsed (and invalid entries logged) by `SettingsLoader`; `WolfFormManager` reads the parsed values from `Settings.wolfForm()`/`diet()`. `listeners/WerewolfRestrictionListener` enforces `BlockedCommands.*` (bypass: `werewolf.bypass.blockedcommands`), blocked potions, the `Diet.*` settings, and vetoes turning into a wolf in creative/spectator.


**Storage.** `storage/` owns the data files; managers never touch YAML. `Storage` reads all four files into memory at startup: `werewolves.yml` → `WerewolfRepository` of `WerewolfRecord` (keyed by UUID: `PlayerName`, `WolfState`, `Clan`, `WerewolfName`, `Transformations`, `LastTransform`, `InfectedDate`, `InfectedThisNight`, `LastLevelNight`, `Intent`, `OriginalGroup`), `clans.yml` → `ClanRepository`/`ClanRecord` (`Alpha`, `Home.*`, `LastCallTime`; clan points are memory only), `hunters.yml` → `HunterRepository`/`HunterRecord` (by name: `Kills`, `LastKill`), `trophies.yml` → `TrophyRepository` (position hash → `Description` lore list). The files keep their old keys and format; keys a repository doesn't know (top-level or inside a record) are written back unchanged. Managers get their repository through the constructor and change records through setters, which mark the repository dirty. `Storage.flush()` (every 3600 ticks, `/ww save`, and from `close()` in `onDisable`) snapshots dirty repositories to YAML text on the main thread and writes them on one background thread to `<file>.tmp` + atomic move; `close()` waits up to 15 s. A file that fails to parse is logged as SEVERE, copied to `<file>.broken-<timestamp>`, and that repository becomes read-only (empty, never saved) until a reload reads it successfully. `Storage.reload()` re-reads only files whose modification time changed since the plugin last read/wrote them (hand edits win over unsaved changes), then flushes the rest. `TrophyManager` tags the heads it makes (`WerewolfTrophy`) and only remembers the lore of those (or of gold "… Head" items from older versions). A werewolves.yml entry is created only by `WerewolfManager.makeWerewolf`; every other setter ignores players without one, and reads (`getWerewolfClan`, `isWerewolf`, …) never write (non-werewolves get `WerewolfBite`; werewolves without a clan in old data get a random one at load). `unmakeWerewolf` removes the entry and the in-memory wolf-form state immediately; the `UndisguiseTask` it schedules (`undisguiseCuredWerewolf`) only restores the skin, name and permission group.

**Package roles:**
- `managers/` hold state and logic; persistent state lives in `storage/` repositories (above).
- `listeners/` turn Bukkit events into manager calls.
- `tasks/` are one-off `Runnable`s scheduled with `runTaskLater`. Transforming a player is asynchronous: `disguiseWerewolf()` schedules a `DisguiseTask` (which does nothing if the player is no longer a werewolf), and `undisguiseWerewolf()`/`undisguiseCuredWerewolf()` schedule an `UndisguiseTask`.
- `commands/Commands.java` handles `/werewolf` (`/ww`), `/growl` and `/howl` in one big `if/else` chain on `args[0]`. Any new subcommand also needs a `usage` entry and its permission nodes in `src/resources/plugin.yml`.

**Disguises.** `disguises/WerewolfDisguiseAPI` hides which skin backend is in use. `init(backend)` runs after config is loaded and takes `Disguises.Backend`: `auto` picks `PaperSkinFactory` (built in, uses Paper's `Player#setPlayerProfile`) on Paper, otherwise `LibsDisguisesFactory`, then `SkinsRestorerFactory`; `builtin`/`libsdisguises`/`skinsrestorer` force one. All implement `IWerewolfDisguiseFactory`. If none is usable, `disguisesEnabled` is false and werewolves keep their normal skin. `WerewolfDisguiseAPI.getBackend()` says which one is active (the arm-swing hit workaround in `PlayerListener` only runs for LibsDisguises). The werewolf skin textures and signatures, and the fake account names/UUIDs for the four werewolf types (Alpha, Witherfang/potion, Bloodmoon/WerewolfBite, Silvermane/WildBite), are `Clans.*` keys at the bottom of the bundled config.yml (`Settings.clans()`; `ConfigMigrator` swaps them back in configs from before Bloodmoon and Silvermane got their own skins).

**Custom items.** Silver sword, silver armor, wolfbane, infection/cure potions, the lore book and the werewolf/vampire tracker compasses get a `PersistentDataContainer` tag (key `werewolf:ww-item`) in `ItemManager`. Code checks that tag to recognize an item, not its display name. Crafting recipes are in `items/Recipes.java`, and each one is turned on or off by an `Items.Craftable*` key (`Settings.items().craftable*()`).

**Hunting gear.** All four silver armor pieces share the `SilverArmor` tag; `ItemManager.ArmorPiece` maps the slot worn to its `Items.SilverArmor.<Piece>.Purity/Defense`. Purity (summed %) is the chance to cancel a bite infection (`HuntingGearListener`, and `integrations/VampireIntegration` for VampireRevamp infections); defense is applied in `DamageListener.applySilverArmor` against werewolf/vampire attackers. Only humans (`WerewolfAPI.isHuman`) may wear it or use/craft trackers. Silver sword hits on wolf form skip the clan defence and take `SilverSwordMultiplier` in `DamageListener` (not in `DamageManager.getDamageFromItemInHand`). One sync task in `onEnable` runs every 20 ticks: `TrackerManager.update` (tracker compass locks), `ScentManager.update` (`/ww track` particle trail, sniffed targets) and `ItemManager.update` (silver sword penalty, taking silver armor off non-humans). Tracker locks, scent targets and sniff cooldowns are in memory. `TrackerTargetEvent` and `WerewolfSniffEvent` are cancellable hooks for region/PvP plugins.

**Integrations.** `integrations/` holds one `IntegrationListener` per optional region/PvP plugin; these classes reference the other plugin's classes, so `onEnable` only constructs them after detecting the plugin (never reference them, or the plugin's classes, from always-loaded code), registers them, and calls `shutdown()` in `onDisable`. They read their `Integrations.*` toggle at event time, so `/ww reload` works. `WorldGuardIntegration` and `PvPManagerIntegration` (4.x `me.chancesd` API only) veto trackers/sniffs into protected players; `ForcePvPIntegration` (needs PvPManager + GriefPrevention, `Hunting.ForcePvP.*`, default off) forces PvP on for players in claims they have no trust in, remembering only the players it forced so it can switch them back on leaving/quit/disable. `VampireIntegration` (VampireRevamp) keeps anyone from being both: a werewolf's vampire infection is reset to 0 and its vampire type change cancelled, and vampires can't get the werewolf infection; `WerewolfManager.update()` still cures the werewolf side of hybrids made before that. (`WerewolfAPI.isVampire` calls `VampireAPI` but only behind the `vampireEnabled` check.) Bite infections run in `DamageListener.onBite` at MONITOR with `ignoreCancelled`, so hits cancelled by any protection plugin never infect.

**Localization.** The repo's `lang/` folder is bundled into the jar. `LanguageManager` reads `plugins/Werewolf/lang/<language>.yml`, copying the bundled file there first if it is missing, so server admins can edit it. Keys missing from that file fall back to the bundled file for the same language, then to bundled `english.yml`. Each language key is a `LANGUAGESTRING` enum constant whose name matches a top-level YAML key holding a list of variants (one is chosen at random). Placeholders such as `$PlayerName`, `$Amount`, `$Type` and `$ServerName` are filled from fields set right before the lookup. A new message needs an enum constant plus an entry in `lang/english.yml` (other languages fall back to it). Without the english entry players see `<KEY> MISSING`.
