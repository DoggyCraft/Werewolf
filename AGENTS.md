# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Werewolf is a Spigot/Bukkit Minecraft server plugin (`com.dogonfire.werewolf`), built with Maven against `paper-api` 26.3 but running on Minecraft 1.21.3 and newer (including 26.x; `api-version: '1.21'` in `plugin.yml`). It must still run on Spigot: the only Paper-only API calls live in `disguises/PaperSkinFactory`, which is only loaded after a runtime check. It is built with JDK 25 but targets Java 21 (`maven.compiler.release` in the root `pom.xml`), since 1.21.x servers run on Java 21. 1.21.3 is the floor: before it `Attribute` and `Sound` were enums and the attributes had `GENERIC_` names, which a jar compiled against 26.x can't link against. CI (`.github/workflows/build.yml`) builds on JDK 25 for every push and PR and runs `ci/LinkCheck.java` (see **Commands**); pushing a tag equal to the pom version (e.g. `1.0.0`) publishes a GitHub release with the plugin and API jars.

## Modules

A Maven multi-module build (standard Maven layout in each module):
- Root `pom.xml` (`com.dogonfire:werewolf-parent`, packaging `pom`): the version, shared properties (`spigotAPIVersion`, `paperAPIVersion`, `maven.compiler.release`), the spigotmc/papermc repositories and `pluginManagement` (maven-shade must stay 3.6.2+; 3.6.0 breaks on Java 25).
- `api/` (`werewolf-api`): only `com.dogonfire.werewolf.api` and `api.event`, in `api/src/main/java/`. It depends on nothing but `spigot-api` 1.21.3 (the oldest supported version), so **API code can only use the Spigot API**: no Paper-only types, nothing from the plugin module. Every build also makes sources and javadoc jars; javadoc runs with `doclint all,-missing`, so broken javadoc fails the build.
- `plugin/` (`werewolf`, jar `plugin/target/Werewolf-<version>.jar`): everything else, in `plugin/src/main/java/com/dogonfire/werewolf/` (package paths like `managers/` or `disguises/` below are relative to it). It depends on `werewolf-api` (compile scope, shaded into the jar, not relocated), bStats (`org.bstats:bstats-bukkit`, shaded and relocated to `com.dogonfire.werewolf.libs.bstats`, which bStats requires), paper-api and the optional plugins (all `provided`, repos in `plugin/pom.xml`). Resources are in `plugin/src/main/resources/`: `plugin.yml` (the only Maven-filtered file, gets `${project.version}`), `config.yml` and `lang/*.yml` (copied as-is). The deprecated `WerewolfAPI` facade stays in the plugin module because it delegates into internals.

## Commands

```bash
nix develop                # devshell with JDK 25 + Maven (flake.nix); prefix commands with `nix develop -c` otherwise
mvn clean package          # default goal, from the root; builds api/target/werewolf-api-<version>{,-sources,-javadoc}.jar and plugin/target/Werewolf-<version>.jar
mvn -B clean package       # what CI runs (there are no unit tests; this checks compilation and API javadoc)
mvn -q -pl api dependency:build-classpath -Dmdep.outputFile=target/spigot.classpath \
  && java ci/LinkCheck.java plugin/target/Werewolf-*.jar "$(cat api/target/spigot.classpath)"  # after package: the jar may only use API the oldest supported Spigot has (CI runs this too)
```

- **Newer API than 1.21.3.** The plugin compiles against paper-api 26.3, so it can name things 1.21.3 doesn't have; `ci/LinkCheck.java` resolves every `org.bukkit`/`net.md_5` class, field and method the jar references against spigot-api 1.21.3 and fails on anything missing (or on a class called as an interface, the old enums). Materials, sounds, mobs and other constants newer than 1.21.3 are looked up by name at runtime with a fallback (`Material.matchMaterial`, `Registry.SOUNDS.get(NamespacedKey.minecraft(...))`, see `DamageListener.GOLDEN_SPEAR` and `WerewolfManager.howlSound`), and a method whose return type was narrowed later is called through the type that declares the old signature (`((EntityEvent) event).getEntity()` for `EntityPotionEffectEvent`). Config names (mobs, materials, effects) are parsed at load and unknown ones skipped with a warning, so the bundled defaults may list mobs newer than 1.21.3. The only classes the check skips are the Paper-only ones in its `PAPER_ONLY` list (now `disguises/PaperSkinFactory` and its nested classes), which are loaded only after `WerewolfDisguiseAPI.isPaper()`; add a class there only if it is guarded the same way.

- There is no test suite. You can only check that it compiles; to check behavior, drop the jar into a Spigot server's `plugins/` folder.
- All plugin dependencies (Vault, LibsDisguises, SkinsRestorer, WorldGuard, PvPManager 4.x, GriefPrevention, PlaceholderAPI, Vampire) are `provided` and resolved from the third-party repos listed in `plugin/pom.xml`. If one of those repos is unreachable, the build fails.
- Releases bump `<version>` in all three poms (root and the `<parent>` of `api/` and `plugin/`, e.g. "Bump to v1.0.0"; between releases the poms carry the next version with `-SNAPSHOT`), then push a tag with exactly that version (e.g. `1.0.0`, no `v`); CI checks the tag against the version, builds, and attaches `Werewolf-<version>.jar` and `werewolf-api-<version>.jar` to a GitHub release. Publishing is JitPack only: `jitpack.yml` downloads Temurin 25 and runs `mvn -B install -DskipTests` on the tag, giving `com.github.DoggyCraft.Werewolf:werewolf-api:<tag>` (and `...:werewolf:<tag>`, whose pom is dependency-reduced). No credentials are needed anywhere. Work goes to the `dev` branch and is merged into `master` through a PR.

## Architecture

**Object graph (no statics).** Nothing is reached through static state; every component gets its dependencies through its constructor.
- `Werewolf.java` (the `JavaPlugin`) owns the lifecycle, the current `config/Settings` (`getSettings()`, replaced on reload, so always read it when needed and never keep it in a field) and the small helpers `log`, `logDebug`, `sendInfo`.
- `WerewolfContext` is the object graph, built once per enable and passed to the constructor of every manager, listener, task and command (`new XListener(ctx)`; commands get it through `SubCommand`'s `ctx` field). Components keep `ctx` (and usually `plugin = ctx.getPlugin()`) and fetch managers at call time: `ctx.getWerewolfManager()`, `ctx.getLanguageManager()`, `ctx.getSettings()`, `ctx.getStorage()`, `ctx.getDisguises()`, … There is no static accessor for it; don't add one.
- Core managers (`LanguageManager`, `PermissionsManager`, `MoonManager`, `WolfFormManager`, `WerewolfManager`, `ClanManager`, `StatisticsManager`, `ItemManager`, `TrackerManager`, `ScentManager`, `SkinManager`, the `WerewolfDisguiseAPI` instance, and `HuntManager` when Vault is present) are created in the `WerewolfContext` constructor and live until disable, so their in-memory state (wolf forms, cooldowns, skins) survives `/ww reload`. Constructors must not call other managers (the graph is still being built); cycles (e.g. `WerewolfManager` ↔ `ClanManager`) are fine because lookups happen at call time.
- Feature managers (`SignManager`, `TrophyManager`, `WerewolfScoreboardManager`) are created and dropped by the plugin according to Settings and may be null: fetch them from `ctx` each time and null-check (`HuntManager` is null without Vault).
- Detected plugins are context flags: `ctx.isVaultEnabled()`, `isVampireEnabled()`, `isHealthBarEnabled()`, `isDisguisesEnabled()`. `ctx.isWerewolvesEnabled()` is the `/ww on|off` switch (most listeners and the update loop do nothing while it is off).
- Vault services are looked up on use, never cached, because the economy/permissions plugin may enable after us: `ctx.getEconomy()` returns null without an economy provider (`HuntManager` and `SignManager` then tell the player `EconomyUnavailable` / keep the bounty instead of paying), and `PermissionsManager` falls back to the plugin.yml defaults without a permission provider.
- Static code that stays: the deprecated `WerewolfAPI` facade (see **Public API**; internal code must not use it), and stateless helpers (`CommandUtil`, `Recipes`, `DamageManager`, `SettingsLoader.matchEffectType`).

**Lifecycle.** `onEnable`: `loadSettings()` (migrator + `SettingsLoader`) → `new Storage(...).load()` → `new WerewolfContext(...)` (builds the core managers) → `ClanManager.load()`, `WerewolfManager.refreshAllProfiles()`, `MoonManager.snapshotPhases()`, `LanguageManager.load()`, disguise backend init → commands → always-on listeners (`Player`, `Interact`, `Damage`, `WerewolfRestriction`, `HuntingGear`, `Alpha`, `Inventory`) → PlaceholderAPI expansion → core repeating tasks (update loop 100 ticks, storage flush 3600 ticks, gear loop 20 ticks) → `startFeatures()` → the `WerewolfService` is registered in the ServicesManager and set on `WerewolfAPI` (last, so other plugins only see a loaded plugin) → `startMetrics()` (bStats plugin id 35251; the custom charts read Settings/context when bStats collects them, so they follow reloads; admins opt out in `plugins/bStats/config.yml`, there is no Werewolf key). `startFeatures()` creates what Settings switch on and records it for `stopFeatures()`: `SignManager` (`Signs.Enabled`), `TrophyManager` (`Trophies.Enabled`), `ChatListener` (`Settings.WolfChat`), the clan update task (`Clans.Enabled`, 72000 ticks), the recipes (`ItemManager.addRecipes`, per `Items.Craftable*`; `removeRecipes` calls `Bukkit.removeRecipe` for each key it added), the integrations, and the scoreboard manager (`Scoreboards.Enabled`; kept as is across a reload that leaves it on, so the sidebars keep their counts). `onDisable` runs in reverse: the service is unregistered and cleared from `WerewolfAPI` first → `Metrics.shutdown()` → `stopFeatures()` → `HuntManager.stop()` (compass task), scent/tracker state cleared → `WerewolfManager.untransformAllForShutdown()` (everyone in wolf form goes back to human synchronously: delayed tasks would never run, and werewolves.yml is then saved with them in human form) → scoreboards stopped → expansion unregistered → `cancelTasks`/`unregisterAll` → `Storage.close()` (after the untransforms).

**Reload.** `/ww reload` (`Werewolf.reload()`): `reloadConfig()` + migrator + `SettingsLoader` → `LanguageManager.load()` → `Storage.reload()` → `ClanManager.load()` (clan names) → `WerewolfManager.refreshAllProfiles()` → if `Disguises.Backend` changed, everyone in wolf form is undisguised with the old backend, the backend is re-initialised and they are re-skinned without transformation messages, otherwise `WerewolfDisguiseAPI.reloadSkins()` (SkinsRestorer registers the changed `Clans.*` skins again) → `stopFeatures()` + `startFeatures()`. Werewolves stay in wolf form; core managers and their state are untouched. Everything else reads Settings at use time, so every config key takes effect on reload.

**Adding things.**
- A manager: give it a `(WerewolfContext ctx, …)` constructor, create it in the `WerewolfContext` constructor (core, with a getter) or in `startFeatures`/`stopFeatures` (feature: package-private setter on the context, null when off). If it holds tasks or changes players, give it a stop method and call it from `onDisable`/`stopFeatures`.
- A listener: `(WerewolfContext ctx)` constructor; register it in `onEnable` if always on, or with `registerFeature(...)` in `startFeatures` if a setting switches it (it is then unregistered on reload/disable).
- A repeating task: `runTaskTimer` in `onEnable` (core) or add the `BukkitTask` to `featureTasks` in `startFeatures`. One-off tasks in `tasks/` take `ctx` too.
- A command: see `commands/` below. A config key: see **Configuration** (a key that switches a component on or off is read in `startFeatures`). A message: see **Localization**.

**Configuration.** `plugin/src/main/resources/config.yml` is the single source of defaults: every key with its default and a comment (it is not Maven-filtered; only plugin.yml is). `saveDefaultConfig()` writes it on first start; after that Bukkit uses the bundled file as defaults, so keys missing from the admin's file get the bundled value. The plugin never rewrites config.yml except in `config/ConfigMigrator`, which runs at every (re)load: it reads `config-version` (missing = 1), backs up the old file once to `config.v<old>.bak`, upgrades it step by step (v1→v2: `WerewolfWolf.*`/`Infection.CurePotionChance` renames, swapped Bloodmoon/Silvermane skins, removing dead keys; v2→v3: `Clans.<X>SkinValue/SkinSignature` move to `Clans.Skins.<X>.Value/Signature` and `Clans.AlphaSkin.*`, the skin account names/UUIDs are deleted; v3→v4 only sets the version, the new `Werewolf.KillHealing`/`Clans.MobPoints` come from the bundled file) and writes it atomically; it refuses to touch a file that does not parse. `config/SettingsLoader` then builds the immutable `config/Settings` record (one nested record per section: `general()` = `Settings.*` plus the one-key sections, `moon()`, `wolfForm()`, `infection()`, `items()`, `clans()`, …), clamping/logging invalid values and parsing effects, materials, UUIDs and enums. It reads keys without Java defaults (`getInt(path)`), except per-clan `Werewolf.Stats.*` which fall back to the global `Werewolf.*` values when the file does not set them. Map sections whose keys are data (mob names) are read with `SettingsLoader.section(path)`: the admin's section as is if the file has it (no fill-in from the bundled one), otherwise the bundled section whole (Bukkit's `getConfigurationSection` would return an empty section there). To add an option: add the key to config.yml, a record component in `Settings`, and read it in `SettingsLoader`; if a key is renamed or removed, bump `ConfigMigrator.CURRENT_VERSION` and `config-version`, and add a migration step. `/ww reload` re-runs all of this; see **Reload**.

**Main game loop.** A sync repeating task calls `WerewolfManager.update()` every 100 ticks. It checks every online werewolf for transform/untransform, and gives one random player a chance at an "urge" message. That method handles night/full-moon transformations, the `/ww transform` time limit, infection progress and auto-cure. Moon phase and night timing live in `managers/MoonManager` (`getMoonPhase`, `isNight`, `isFullMoonNight`, `isTransformationNight` = the nights the moon forces outdoor werewolves to transform, `setMoonPhase`, dusk announcements); `isUnderOpenSky`, `isWerewolvesAllowedInWorld` (`AllowedWorlds`; empty = the main world), `transform`/`untransform` (smoke effect + `setWerewolfSkin`/`unsetWerewolfSkin`) and `isVampire`/`isHuman` are on `WerewolfManager`. Clans update on a separate 72000-tick task (only while `Clans.Enabled`).

**Levels.** A werewolf's level is `WerewolfManager.getNumberOfTransformations` (`Transformations` in `werewolves.yml`); `Maturity.*` config keys are the levels that unlock perks. Every level change goes through `WerewolfManager.setLevel(id, level, cause)` (fires `WerewolfLevelChangeEvent`). `grantFullMoonLevel` adds one level per transformation night, guarded by `LastLevelNight` so relogging doesn't grant more (the night is used up even if the event is cancelled). Wolf forms entered with `Reason.CONTROLLED` are tracked in memory: they are not reverted at morning but expire after the `Transformation.*` time limit (`Reason.TIME_LIMIT`); wolf forms entered with `Reason.API` (`heldForms`) last until something untransforms them; every other wolf form is reverted at morning. Cooldowns (transform/howl/growl) are in memory too.

**Alphas.** Each clan's alpha UUID is in `clans.yml` (`ClanManager.getAlpha` is a plain read). `ClanManager.checkAlphas()` runs from `WerewolfManager.update()` and fills empty or stale slots with `WerewolfManager.getAlphaCandidate` (full werewolves first, then highest level); `setWerewolfClan` and `unmakeWerewolf` (via `removeAlpha`) hand the slot on immediately. `listeners/AlphaListener` moves the alpha to a same-clan killer, or to the runner-up when a human kills the alpha (`Hunting.Enabled`), and on `NewAlphaEvent` (MONITOR) re-skins the old and new alpha a tick later through `WerewolfManager.refreshWerewolfSkin` (`Reason.REFRESH`). Admin commands `setlevel`/`addlevel`/`setalpha`/`cure` resolve names through werewolves.yml and known offline players, so they work on offline werewolves.

**Events.** `api/event/` holds cancellable Bukkit events fired at the choke points (plus `TrackerTargetEvent` and `WerewolfSniffEvent`, see Hunting gear): `WerewolfInfectionEvent` (`WerewolfManager.makeWerewolf`; bites pass the configured risk as the event's adjustable `chance` and the roll happens after the event, then silver armor's purity roll), `WerewolfCureEvent` (`unmakeWerewolf`), `WerewolfTransformEvent` (`setWerewolfSkin`/`unsetWerewolfSkin`, cancelling is ignored for `Reason.FORCED`), `WerewolfLevelChangeEvent` (`setLevel`) and `NewAlphaEvent` (`ClanManager.assignAlphaInClan`, with a `Cause`). Each of those methods takes a reason/cause and returns whether it went ahead; new code that changes werewolf state should go through them, and features that need to veto or react to a change should listen to these events instead of adding checks at every call site.

**Public API (the contract with other plugins; change it with care).** `com.dogonfire.werewolf.api` and `api.event` are what other plugins compile against. They live in the `api/` module, published through JitPack as `com.github.DoggyCraft.Werewolf:werewolf-api:<tag>`. The module compiles against spigot-api 1.21.3, so they can only use the Spigot API. Keep them free of internal types (no managers, context, storage, Settings), never rename or remove public types, methods or enum constants there (add instead, and deprecate), keep `Clan`/`MoonPhase` constant names (they are also data and config keys), and give every public member javadoc including its threading rule. Contents: `WerewolfService` (implemented by `WerewolfServiceImpl` in the root package, registered in the ServicesManager at the end of `onEnable` and unregistered first in `onDisable`), `WerewolfProfile` (immutable record), `Form`, `Clan`, `MoonPhase`, `WerewolfItem`, `ActionResult`, and the events. Service actions check preconditions (to return a precise `ActionResult`), require the main thread, and call the same choke points as the game with the `API` reason/source/cause, so a vetoed event yields `CANCELLED`. `WerewolfServiceImpl` must not add logic of its own beyond that; behaviour belongs in the managers. The deprecated static `WerewolfAPI` keeps its old signatures (only `getWerewolfClan` now returns `api.Clan`) and delegates to the service; while the plugin is disabled its reads return false/null/0 and its actions do nothing.

**Thread-safe snapshots.** `WerewolfManager` keeps a `ConcurrentHashMap<UUID, WerewolfProfile>` (`getProfile`, `getProfiles`) rebuilt on the main thread whenever a werewolf changes: `WerewolfRepository`'s change listener fires on every record create/setter/remove, `popPlayerData` covers the form, `ClanManager.assignAlphaInClan` the alpha, and `refreshAllProfiles()` runs after (re)loading the data files. New werewolf state that the profile exposes must keep it up to date. `MoonManager.snapshotPhases()` (every update) feeds `getPhaseSnapshot`, and `ClanManager` clan names are an immutable map replaced on load. The service's thread-safe reads and `utils/WerewolfPlaceholderExpansion` (`%werewolf_clan|clan_name|clan_id|werewolf|form|level|alpha|infected|name|moonphase%`, called from any thread) only read these.


**Wolf form.** `managers/WolfFormManager` owns what wolf form does to a player: per-clan `Stats` (speed, defense = multiplier on incoming damage, fist/item damage; separate alpha values, read in `DamageListener`), per-clan potion effects (`Werewolf.Effects.<Clan>`, `NAME:amplifier:duration`), blocked potions and the diet's food list. `DisguiseTask` calls `applyWolfForm`, `WerewolfManager.update()` calls `refreshWolfForm` for everyone in wolf form, and `UndisguiseTask`/join call `removeWolfForm`, which removes only the effects it applied. Nobody stays in wolf form while offline: `PlayerListener.onPlayerQuit` → `WerewolfManager.untransformOnQuit` turns them human in the same tick (FORCED), so the human walk speed, effects and permission group are what gets saved. `onPlayerJoin` → `repairOnJoin` cleans up what crashes, older versions or offline cures left (a stored `WolfForm`, werewolf skins kept by SkinManager or the backend, e.g. a SkinsRestorer custom skin, the werewolf group, and for non-werewolves a wolf form walk speed with its effects); then `CheckTransformationTask` transforms them if it is time. Respawn also only schedules `CheckTransformationTask`. `InfectedThisNight` (set on infection and on death in wolf form) blocks transforming until the next non-FORCED untransform, normally the morning one; FORCED changes (join, quit, death, world change, shutdown) don't clear it. `OriginalGroup` is never overwritten with the werewolf group, and turning human removes the werewolf group (`PermissionsManager.leaveWerewolfGroup`). The config lists are parsed (and invalid entries logged) by `SettingsLoader`; `WolfFormManager` reads the parsed values from `Settings.wolfForm()`/`diet()`. `listeners/WerewolfRestrictionListener` enforces `BlockedCommands.*` (bypass: `werewolf.bypass.blockedcommands`), blocked potions, the `Diet.*` settings, and vetoes turning into a wolf in creative/spectator.

**Kills.** What a kill is worth is config, not code: `Werewolf.KillHealing` (health a werewolf in wolf form regains, `Settings.wolfForm().killHealing()`, used in `DamageListener.onEntityDeath`) and `Clans.MobPoints` (clan points, `Settings.clans().mobPoints()`, used in `ClanManager.handleMobKill`). Both map `EntityType` names to values, with a `default` entry for unlisted mobs (healing 0, points 0.5 as before); `SettingsLoader.mobTable` skips unknown names (with one warning per section listing them, since older servers lack the newest mobs) and clamps negatives with a warning. A new mob in a Minecraft update only needs a line in the bundled config.yml.

**Storage.** `storage/` owns the data files; managers never touch YAML. `Storage` reads all four files into memory at startup: `werewolves.yml` → `WerewolfRepository` of `WerewolfRecord` (keyed by UUID: `PlayerName`, `WolfState`, `Clan`, `WerewolfName`, `Transformations`, `LastTransform`, `InfectedDate`, `InfectedThisNight`, `LastLevelNight`, `Intent`, `OriginalGroup`), `clans.yml` → `ClanRepository`/`ClanRecord` (`Alpha`, `Home.*`, `LastCallTime`; clan points are memory only), `hunters.yml` → `HunterRepository`/`HunterRecord` (by name: `Kills`, `LastKill`; plus the bounty pool under the top-level key `total-bounty`), `trophies.yml` → `TrophyRepository` (position hash → `Description` lore list). The files keep their old keys and format; keys a repository doesn't know (top-level or inside a record) are written back unchanged. Managers get their repository through the constructor and change records through setters, which mark the repository dirty. `Storage.flush()` (every 3600 ticks, `/ww save`, and from `close()` in `onDisable`) snapshots dirty repositories to YAML text on the main thread and writes them on one background thread to `<file>.tmp` + atomic move; `close()` waits up to 15 s. A file that fails to parse is logged as SEVERE, copied to `<file>.broken-<timestamp>`, and at startup that repository becomes read-only (empty, never saved) until a reload reads it successfully. Files are parsed before the data in memory is replaced, so a file broken by a hand edit before `/ww reload` keeps the loaded data, stays writable and is written again from memory (the broken file is copied as above). `Storage.reload()` re-reads only files whose modification time changed since the plugin last read/wrote them (hand edits win over unsaved changes), then flushes the rest. `TrophyManager` tags the heads it makes (`WerewolfTrophy`) and only remembers the lore of those (or of gold "… Head" items from older versions). A werewolves.yml entry is created only by `WerewolfManager.makeWerewolf`; every other setter ignores players without one, and reads (`getWerewolfClan`, `isWerewolf`, …) never write (non-werewolves get `WerewolfBite`; werewolves without a clan in old data get a random one at load). `unmakeWerewolf` removes the entry and the in-memory wolf-form state immediately; the `UndisguiseTask` it schedules (`undisguiseCuredWerewolf`) only restores the skin, name and permission group.

**Package roles:**
- `managers/` hold state and logic; persistent state lives in `storage/` repositories (above).
- `listeners/` turn Bukkit events into manager calls.
- `tasks/` are one-off `Runnable`s scheduled with `runTaskLater`. Transforming a player is asynchronous: `WerewolfManager.disguiseWerewolf()` schedules a `DisguiseTask` (which does nothing if the player went offline, is no longer a werewolf or is already in wolf form), and `undisguiseWerewolf()`/`undisguiseCuredWerewolf()` schedule an `UndisguiseTask` (run immediately while the plugin is disabling or the player is quitting). `CompassTrackerTask` (`/ww hunt` compasses) is owned by `HuntManager`, runs only while someone hunts and is stopped on disable.
- `commands/`: `WerewolfCommand` is the `/werewolf` (`/ww`) executor and registry. No arguments shows `InfoScreen`; otherwise it finds the `SubCommand` (in `commands/sub/`, one class per command; `GiveItemCommand`, `SetLevelCommand` and `PluginToggleCommand` are parameterised) by `args[0]`, rejects arities the command doesn't accept (`acceptsArgs`, counting args[0]; `InvalidCommand` for 1–2 args, plugin.yml usage for more), then checks console use (`isPlayerOnly`) and permission (`isPermitted`: node, op or console) centrally before `execute`. Registration order is the `/ww help` order; help lines come from each command's usage + help language key, tab completion of args[0] from `isListed` (permission + `isAvailable`, e.g. clans enabled). `/growl` and `/howl` are `SubCommand`s run through `SingleCommandExecutor`. Shared lookups (offline player names, clan parsing, permission check) are static helpers in `CommandUtil` that take the context. A new subcommand needs a class with a `(WerewolfContext ctx)` constructor calling `super(ctx, name, permission, playerOnly, usage, helpKey)` (it then has `ctx`, `plugin`, `lang()`, `text()`, `send()`), a `register(new XCommand(ctx))` line in `WerewolfCommand`, and a `usage` entry plus permission nodes in `plugin/src/main/resources/plugin.yml`.

**Disguises.** `disguises/WerewolfDisguiseAPI` (one instance, `ctx.getDisguises()`) hides which skin backend is in use. `init(backend)` runs on enable after config is loaded (and again on `/ww reload` when the setting changed, see **Reload**) and takes `Disguises.Backend`: `auto` picks `PaperSkinFactory` (built in, uses Paper's `Player#setPlayerProfile`) on Paper, otherwise `LibsDisguisesFactory`, then `SkinsRestorerFactory`; `builtin`/`libsdisguises`/`skinsrestorer` force one. All implement `IWerewolfDisguiseFactory`; their disguises extend `WerewolfDisguise`, which is just (clan, alpha flag) plus the context and reads its texture from Settings at use time (`getSkin()` → `Settings.clans().skin(clan, alpha)`). `SkinManager` picks the disguise (`getDisguise(clan, alpha)`, a new cheap object each time; alpha = `Clans.Enabled` and `ClanManager.isAlpha`) and `WerewolfDisguiseAPI` remembers the one each player wears. **Every backend is texture-only; no Minecraft account is involved:** Paper sets the `textures` property, LibsDisguises gets `new PlayerDisguise(nameProfile, skinProfile)` where the skin profile is a packetevents `UserProfile` carrying `TextureProperty("textures", value, signature)` (so it never looks a skin up at Mojang; plugin.yml soft-depends on `packetevents`, which provides those types), and SkinsRestorer gets custom skins registered from the textures: one per clan named after the `Clan` constant and one per clan alpha named `Alpha_<Clan>` (registered when the factory is created and again on `/ww reload` via `reloadSkins`; werewolves already in wolf form keep the old skin until they transform again; `clearLeftover` also recognises the shared `Alpha` skin of older versions). `isWerewolfTexture` (Paper) covers every clan and alpha texture. If none is usable, `ctx.isDisguisesEnabled()` is false and werewolves keep their normal skin. `getBackend()` says which one is active (the arm-swing hit workaround in `PlayerListener` only runs for LibsDisguises). The skins are config keys (`Settings.clans()`): `Clans.Skins.<Clan>.Value/Signature` per clan, an optional `Clans.Skins.<Clan>.Alpha.Value/Signature` (used only when both are set, otherwise the clan's alpha wears `Clans.AlphaSkin`); `SettingsLoader` resolves that fallback into `alphaSkins`. The default textures were taken from the accounts WF_Werewolf (Witherfang/Potion), BM_Werewolf (Bloodmoon/WerewolfBite), SM_Werewolf (Silvermane/WildBite) and WerewolfAlpha (alpha), as the config.yml comments say; only the Value/Signature is used, so those accounts don't need to exist or keep the skin. Trophy heads (`TrophyManager.skinProfile`) also use only the texture.

**Custom items.** Silver sword, silver armor, wolfbane, infection/cure potions, the lore book and the werewolf/vampire tracker compasses get a `PersistentDataContainer` tag (key `werewolf:ww-item`) in `ItemManager`. Code checks that tag to recognize an item, not its display name. `ItemManager.newItem`/`getItemType` map the tags to `api.WerewolfItem` for the API (silver armor pieces by material). Crafting recipes are in `items/Recipes.java`, and each one is turned on or off by an `Items.Craftable*` key (`Settings.items().craftable*()`); `ItemManager.addRecipes`/`removeRecipes` add and remove them (on enable, reload and disable).

**Hunting gear.** All four silver armor pieces share the `SilverArmor` tag; `ItemManager.ArmorPiece` maps the slot worn to its `Items.SilverArmor.<Piece>.Purity/Defense`. Purity (summed %) is the chance to cancel a bite infection (rolled in `WerewolfManager.makeWerewolf` after the infection event and its chance roll, and in `integrations/VampireIntegration` for VampireRevamp infections); defense is applied in `DamageListener.applySilverArmor` against werewolf/vampire attackers. Only humans (`WerewolfManager.isHuman`) may wear it or use/craft trackers. Silver sword hits on wolf form skip the clan defence and take `SilverSwordMultiplier` in `DamageListener` (not in `DamageManager.getDamageFromItemInHand`). One sync task in `onEnable` runs every 20 ticks: `TrackerManager.update` (tracker compass locks), `ScentManager.update` (`/ww track` particle trail, sniffed targets) and `ItemManager.update` (silver sword penalty, taking silver armor off non-humans). Tracker locks, scent targets and sniff cooldowns are in memory. `TrackerTargetEvent` and `WerewolfSniffEvent` are cancellable hooks for region/PvP plugins.

**Integrations.** `integrations/` holds one `IntegrationListener` per optional region/PvP plugin; these classes reference the other plugin's classes, so `Werewolf.startIntegrations` only constructs them after detecting the plugin and when their `Integrations.*` toggle is on (never reference them, or the plugin's classes, from always-loaded code), registers them, and `stopFeatures` unregisters them and calls `shutdown()` (on disable and on `/ww reload`, which then starts them again per the new settings). `WorldGuardIntegration` and `PvPManagerIntegration` (4.x `me.chancesd` API only) veto trackers/sniffs into protected players; `ForcePvPIntegration` (needs PvPManager + GriefPrevention, `Hunting.ForcePvP.*`, default off) forces PvP on for players in claims they have no trust in, remembering only the players it forced so it can switch them back on leaving/quit/disable. `VampireIntegration` (VampireRevamp) keeps anyone from being both: a werewolf's vampire infection is reset to 0 and its vampire type change cancelled, and vampires can't get the werewolf infection; `WerewolfManager.update()` still cures the werewolf side of hybrids made before that. (`WerewolfManager.isVampire` calls `VampireAPI` directly, but only behind the `ctx.isVampireEnabled()` check, so the class is never loaded without VampireRevamp.) Bite infections run in `DamageListener.onBite` at MONITOR with `ignoreCancelled`, so hits cancelled by any protection plugin never infect.

**Localization.** `plugin/src/main/resources/lang/` is bundled into the jar. `LanguageManager` reads `plugins/Werewolf/lang/<language>.yml`, copying the bundled file there first if it is missing, so server admins can edit it. Keys missing from that file fall back to the bundled file for the same language, then to bundled `english.yml`. Each language key is a `LANGUAGESTRING` enum constant whose name matches a top-level YAML key holding a list of variants (one is chosen at random). Placeholders such as `$PlayerName`, `$Amount`, `$Type` and `$ServerName` are filled from fields set right before the lookup (main thread only: `LanguageManager` is not thread-safe, which is why `ChatListener` does its work in a main-thread task). A new message needs an enum constant plus an entry in `plugin/src/main/resources/lang/english.yml` (other languages fall back to it). Without the english entry players see `<KEY> MISSING`.
